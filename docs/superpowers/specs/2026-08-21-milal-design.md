# 밀알 (Milal) — 설계 문서

작성일: 2026-08-21

## 1. 목적

성경의 "한 알의 밀" 비유를 바탕으로, 소그룹(약 30명)이 **공동체 밀알 하나**를 함께 키우는 웹앱.
구성원이 매일 성경읽기와 다짐을 체크하고, 기도부탁·권유 활동을 요청하면 포인트가 하나의 총점에 합산된다.
총점에 따라 밀알이 5단계로 자라며, 1000점에 도달하면 결실한다. 1회성 캠페인이다.

## 2. 확정된 요구사항

| 항목 | 결정 |
|---|---|
| 형태 | 모바일 우선 웹앱. 로컬 개발·테스트 후 무료 호스팅(Vercel)에 배포, 카카오톡 링크로 공유 |
| 인증 | 사전 등록된 이름만 입력하면 입장. 비밀번호·PIN 없음 (신뢰 기반) |
| 명단 | 테스트용 30명 무작위 한국어 이름 자동 생성. 그중 1명이 관리자 |
| 밀알 | 공동체 밀알 **1개**. 모든 구성원의 포인트가 하나의 총점에 합산 |
| 매일 포인트 | 성경읽기 +1, 다짐 +1. 두 항목은 독립적으로 각각 체크. **한국시간(Asia/Seoul) 기준 하루 1회씩** |
| 요청 포인트 | 기도부탁 +3, 비대면 권유 +5, 대면 권유 +7. 횟수 제한 없음. 관리자 승인 시에만 반영, 거절 시 0 |
| 요청 내용 | 종류 + 요청자 이름 + 시각만. 자유 텍스트 없음 |
| 요청 처리 후 | 승인/거절 후 대기 목록에서 제거. 승인 건은 포인트 기록(ledger)에만 남음 |
| 단계 | 0–199 (1) / 200–399 (2) / 400–699 (3) / 700–999 (4) / 1000+ (5) |
| 1000점 이후 | 점수는 계속 누적, 화면은 5단계(결실) 유지. 초기화 기능은 만들지 않음 |
| 화면 공개 | 모든 구성원이 같은 밭 화면을 봄. 각자의 기여 점수와 오늘 체크 여부도 공개 |
| 일러스트 | 외부 이미지 없이 SVG를 코드에 내장. 화면 품질을 중시 |

## 3. 기술 선택

- **Next.js (App Router) 풀스택** — 프론트와 API를 한 프로젝트에. 배포는 Vercel 1곳.
- **저장소: JSON 문서 키-값 저장** — 테이블·SQL 없음. 인터페이스는 `get(key)` / `set(key, value)` 둘뿐.
  - 로컬: `data/` 폴더에 키별 JSON 파일 (텍스트 에디터로 열어볼 수 있음)
  - 배포: Vercel Blob. 환경변수 하나로 전환
  - 테스트: 메모리 저장소
- **테스트: Vitest** — 규칙 로직 단위 테스트
- **스타일: CSS (Tailwind 또는 CSS Modules), Pretendard 폰트**

선택 이유: 30명·화면 3개 규모에 DB 서버는 과하다. 그러나 무료 호스팅은 디스크가 읽기 전용이거나 재시작 시 초기화되므로
"파일 하나"를 로컬 디스크 대신 Blob에 두는 것만으로 영속성을 확보한다.

## 4. 데이터 모델

저장소 키와 값의 형태. 날짜는 모두 `YYYY-MM-DD` (KST), 시각은 ISO 8601.

```
members : [{ name: string, isAdmin: boolean }]        // 30명 명단
checks/{name} : { [date]: { bible: boolean, resolve: boolean } }
requests : [{ id: string, name: string, kind: RequestKind, requestedAt: string }]
ledger : [{ at: string, name: string, kind: LedgerKind, points: number }]
```

- `RequestKind = "prayer" | "invite_remote" | "invite_face"` → 점수 3 / 5 / 7
- `LedgerKind = "bible" | "resolve" | RequestKind`
- **총점은 저장하지 않는다.** `ledger`의 `points` 합으로 항상 계산한다. 개인 기여 점수도 같은 데이터에서 `name`별 합으로 구한다.
- 동시 쓰기 충돌을 줄이기 위해 `checks`는 사람별 키로 분리한다. `requests`와 `ledger`는 배열이지만 30명 규모에서 충돌 확률이 낮고, 충돌 시 손실은 요청 1건 수준이므로 수용한다.

## 5. 규칙 (서버에서만 판정)

1. **오늘 날짜**는 서버 위치와 무관하게 `Asia/Seoul` 기준으로 구한다. KST 00:00에 새 날이 시작된다.
2. `check(name, kind)`: 오늘 해당 항목이 이미 `true`이면 거부(409). 아니면 `true`로 바꾸고 ledger에 +1 추가.
3. `request(name, kind)`: 제한 없이 `requests`에 추가. 포인트는 아직 반영하지 않음.
4. `decide(id, approve)`: 관리자만 호출 가능. 승인이면 종류별 점수(3/5/7)로 ledger에 추가. 승인·거절 모두 `requests`에서 제거. 점수는 서버가 종류로 결정하며 클라이언트가 보내지 않는다.
5. `stage(total)`: 199→1, 200→2, 399→2, 400→3, 699→3, 700→4, 999→4, 1000→5.
6. 관리자 판정: 요청의 `name`이 `members`에서 `isAdmin: true`인 경우만 허용.

**알려진 한계**: 이름만으로 인증하므로 관리자 이름을 아는 사람이 관리자 API를 호출하는 것을 기술적으로 막지 못한다.
30명 신뢰 기반 모임이므로 수용한다. 필요해지면 관리자 전용 PIN을 추가한다.

## 6. API

| 메서드 | 경로 | 입력 | 출력 |
|---|---|---|---|
| POST | `/api/login` | `{ name }` | `{ ok, isAdmin }` 또는 404 |
| GET | `/api/state?name=` | — | 총점, 단계, 오늘 날짜, 내 오늘 체크, 30명 목록(이름·기여점수·오늘 체크), 내 대기 요청 수, 오늘 참여 인원 |
| POST | `/api/check` | `{ name, kind }` | 갱신된 상태 또는 409 |
| POST | `/api/request` | `{ name, kind }` | `{ ok, pendingCount }` |
| GET | `/api/admin/requests?name=` | — | 대기 목록 (관리자 아니면 403) |
| POST | `/api/admin/decide` | `{ name, id, approve }` | 갱신된 총점 (관리자 아니면 403) |
| POST | `/api/dev/set-total` | `{ name, total }` | **개발 모드 전용.** 단계 일러스트 확인용으로 ledger를 조정. 프로덕션 빌드에는 존재하지 않음 |

## 7. 화면

모바일 세로 기준. PC에서는 가운데 정렬 카드.

### 7.1 입장 `/`
- 은은한 밭·하늘 배경, 제목 "밀알", 한 줄 문구
- 이름 입력 + "들어가기". 명단에 없으면 "명단에 없는 이름입니다"
- 입장 성공 시 이름을 `localStorage`에 저장. 이후 접속은 바로 `/field`로

### 7.2 밭 `/field` (메인)
위에서 아래로:
1. **밀알 일러스트** (화면 높이의 약 절반). 현재 단계 SVG. 하늘·땅·햇빛이 한 장면이며, 단계 상승 시 같은 장면 안에서 변화. 하늘색은 단계 따라 새벽 → 한낮 → 황금빛 노을
2. **진행 표시**: 단계 이름(예: "3단계 · 새싹이 돋았어요"), 총점/1000 진행바, 다음 단계까지 남은 점수
3. **오늘 내 체크**: 큰 버튼 2개 — "📖 성경 읽었어요 (+1)", "✅ 다짐 지켰어요 (+1)". 체크 시 즉시 반영 애니메이션. 완료 항목은 비활성 + "내일 다시"
4. **추가 요청**: 작은 버튼 3개 — 기도부탁(+3) / 비대면 권유(+5) / 대면 권유(+7). 클릭 시 "관리자 확인 후 반영됩니다" 안내. 내 대기 요청 수 표시
5. **함께 자라는 사람들**: 30명 목록. 이름, 기여 점수, 오늘 체크 아이콘(📖 ✅). 오늘 체크한 사람이 위로 정렬
6. 하단 요약: "오늘 N명 참여 · 누적 N점"
- 관리자에게만 상단에 "관리" 링크

### 7.3 관리자 `/admin`
- 비관리자가 접근하면 `/field`로 돌려보냄
- 대기 요청 목록: 이름 · 종류 · 점수 · 요청 시각 · **승인 / 거절** 버튼
- 현황: 총점, 오늘 참여 인원, 최근 반영 기록 20건
- 개발 모드에서만: "테스트용 점수 조정" (200 / 400 / 700 / 1000 점프 버튼)

### 7.4 5단계 일러스트
1. 마른 땅 위의 씨앗, 강한 햇살 — 아직 심기지 않음
2. 씨앗이 땅속에 묻힘 — 단면으로 흙 속 씨앗이 보임
3. 흙을 뚫고 나온 연두색 새싹 두 잎
4. 허리 높이의 초록 밀 줄기, 이삭은 아직 초록
5. 황금빛으로 여문 밀 이삭, 노을, 잔잔한 반짝임

### 7.5 디자인 톤
따뜻한 자연색(흙·밀·하늘), 둥근 카드, 큰 터치 버튼, Pretendard 폰트.
애니메이션은 체크 순간과 단계 상승 순간에만.

```
milal/
  app/
    page.tsx              입장

    admin/page.tsx        관리자
    api/
      login/route.ts
      state/route.ts
      check/route.ts
      request/route.ts
      admin/requests/route.ts
      admin/decide/route.ts
      dev/set-total/route.ts
  lib/
    store/                저장소 인터페이스 + file / blob / memory 구현
    rules.ts              날짜(KST)·체크·요청·승인·단계 계산 — 순수 함수
    members.ts            30명 명단 생성(seed)
  components/
    WheatScene.tsx        단계별 SVG 장면
    ...
  tests/
    rules.test.ts
  data/                   로컬 저장소 (gitignore)
```

규칙 로직(`lib/rules.ts`)은 저장소와 분리된 순수 함수로 두어 테스트가 쉽고, API 라우트는 얇게 유지한다.

## 9. 테스트

### 9.1 자동 (Vitest, 메모리 저장소)
- KST 날짜: UTC 기준 자정 전후 시각에서 KST 날짜가 올바른지, KST 자정 경계에서 날짜가 바뀌는지
- 중복 체크: 같은 날 같은 항목 거부, 다른 항목 허용, 다음 날 재허용
- 요청/승인: 종류별 3/5/7 정확 반영, 거절 시 0점, 처리 후 목록에서 제거
- 단계 경계값: 0, 199, 200, 399, 400, 699, 700, 999, 1000, 1500
- 권한: 비관리자의 관리자 API 거부, 명단 외 이름의 로그인 거부

### 9.2 수동 (로컬 실행 순서)
```
1. cd milal && npm install
2. npm run dev  →  http://localhost:3000
3. 명단에 없는 이름 입력 → 거부 메시지 확인
4. 일반 구성원 이름으로 입장 → 1단계 씨앗 화면 확인
5. 성경·다짐 버튼 클릭 → +2, 버튼 비활성, 새로고침 후 유지 확인
6. 같은 버튼 재클릭 불가 확인
7. 요청 버튼 3종 클릭 → 대기 건수 표시 확인
8. 관리자 이름으로 입장 → "관리" → 승인/거절 → 총점 반영 확인
9. 개발용 점수 조정으로 200/400/700/1000 → 5단계 일러스트 모두 확인
10. 같은 Wi-Fi 폰에서 http://<맥IP>:3000 접속해 모바일 화면 확인
```

## 10. 배포 (구현 완료 후 별도 진행)
GitHub 레포(`SangSusu-git/milal`)를 Vercel에 연결 → Vercel Blob 스토어 생성 → 환경변수 자동 주입 → 배포 URL을 카카오톡에 공유.
이 문서의 범위 밖이며, 구현이 끝난 뒤 안내한다.

## 11. 범위 밖 (만들지 않음)
- 비밀번호/PIN, 세션 만료
- 요청 취소, 승인 취소(되돌리기)
- 밀알 초기화·사이클 반복
- 알림(푸시, 카톡 메시지)
- 다짐 내용 저장, 기도부탁 내용 저장
